# 코드 설명 대본 (임시 초안)

작성: 2026-11-18 · **임시본이다. 본선 발표 준비 때 숫자·역할·문장을 다시 다듬는다.**
숫자는 MODEL_RESULTS 15·16장(본 모델) 기준. `PRESENTATION_NOTES.md` 7장의 예상 질문 표는 예전 모델 숫자라 이 문서를 우선한다.

## 0. 왜 필요한가 (대회 규정)

- "질의응답에서 팀원이 **코드와 모델의 동작을 설명하지 못하면 감점**될 수 있습니다."
- "AI가 **무엇을 받아 무엇을 판단·생성하는지** 설명합니다."
- "외부 API를 쓰면 **API가 맡은 부분과 팀이 만든 부분을 나눠** 설명합니다."
- 생성형 AI 사용은 허용. 사용한 도구와 범위를 발표자료에 적는다.

코드를 한 줄씩 읽어 줄 필요는 없다. **입력 → 판단 → 출력**과 **공정하게 시험한 방법**을 우리 말로 말할 수 있으면 된다.

## 1. 30초 설명 (세 명 모두 외우기)

> 전날 오후 5시에 알 수 있는 정보, 즉 기상청 단기예보, 전력수요, 공휴일, 최근 출력제어 여부, 전력거래소 전망을 넣으면,
> 우리가 학습시킨 트리 모델이 과거 약 1,400일의 패턴을 보고 **내일 육지 출력제어 확률**을 계산합니다.
> 그 확률을 10% 단위와 위험도 4단계로 바꾸고, 어떤 입력이 확률을 올렸는지 **원인 3가지**를 같이 보여 줍니다.
> 외부 API는 날씨와 수요 **자료만** 주고, 예측은 전부 우리 모델이 합니다.

## 3. 파일별 한 줄 설명 (외울 문장)

- **build_clean.py**: "원본은 절대 안 고치고, 형식만 맞춥니다. 빈칸은 0으로 채우지 않고 빈칸으로 둡니다."
- **build_features.py**: "모든 입력은 전날 오후 5시까지 알 수 있는 값만 씁니다. 열마다 언제 알 수 있는지를 문서에 적었습니다."
- **train.py**: "실제 운영처럼 매달 1일에 그 전날까지 자료로만 다시 학습합니다. 그래서 미래 자료가 학습에 섞이지 않습니다."
- **compare_models.py**: "규칙, 로지스틱 회귀, 트리 모델, 신경망 등 10가지를 같은 조건에서 비교했고, 표 자료라 트리 모델(HistGradientBoosting)이 맞았습니다."
- **explain.py**: "입력을 묶음별로 하나씩 평균적인 값으로 바꿔 보고, 확률이 많이 떨어지는 묶음을 원인으로 보여 줍니다."
- **forecast_tomorrow.py**: "기상청 단기예보 API와 전력거래소 실시간 수급에서 자료를 받아, 학습 때와 똑같은 계산으로 내일 확률을 냅니다. 같은 계산인지 44일 × 32항목으로 확인했습니다."
- **build_demo.py**: "결과 파일을 읽어 시연 화면을 만듭니다. 서버 없이 브라우저로 열립니다."

## 4. 모델 핵심 개념 (쉽게)

- **트리 모델(HistGradientBoosting)**: "휴일인가? → 맑은가? → 수요가 낮은가?"처럼 질문을 이어 가는 나무를 수백 개 만들어 합친 모델. 작은 나무(깊이 3) 200개, 학습률 0.05.
- **왜 딥러닝이 아닌가**: 출력제어가 난 날이 백여 일뿐인 표 자료라, 신경망(MLP)은 검증·시험 모두 부스팅보다 낮았다(MODEL_RESULTS 6장, 예전 특징 표 기준이라 본선 전 다시 확인).
- **PR-AUC**: 위험한 날을 위쪽에 잘 올리는지 보는 점수. 출력제어가 드문 자료에서 정확도보다 공정하다. '25 하반기 0.86 vs 규칙 0.52, '26년 0.73 vs 규칙 0.57.
- **경보 기준(임계값)**: 매달, 직전 12개월 결과만 보고 다시 정한다. 그달의 답은 보지 않는다.
- **확률 보정**: 모델 점수를 "실제로 몇 %가 났나"에 맞게 바꾼다(단조 회귀). 40% 이상 예보한 날의 53~54%가 실제로 났다.

## 5. API와 우리 몫 나누기 (규정상 꼭)

| 외부가 하는 일 | 우리가 만든 것 |
| --- | --- |
| 기상청 단기예보 API: 5개 지역 하늘상태·강수확률·최고기온 **자료 제공** | 어떤 지역·시간대를 쓸지 정하고 특징으로 바꾸는 계산 |
| 전력거래소 EPSIS: 5분 단위 전력수요 **자료 제공** | 시간 단위로 맞추는 규칙, 결함 처리 |
| 전력거래소 게시판: 출력제어 전망·실적 **글** | 글 357건의 등록일 전수 확인, 전날 알 수 있던 정보인지 구분 |
| (예측용 외부 AI API 없음) | 모델 학습, 확률·4단계·원인 계산, 시험 설계, 시연 화면 전부 |

## 6. 예상 질문과 답 (본 모델 숫자)

| 질문 | 답 |
| --- | --- |
| 코드를 직접 짰나? | 코드 작성은 생성형 AI(Claude)를 썼고 PPT에 범위를 밝혔다. 팀은 문제 정의, "전날 17시" 예측 시점, 시험 설계, 결과 검토를 했다. *(실제 역할에 맞게 고칠 것)* |
| 답을 미리 본 것 아닌가? | 매달 그 전날까지 자료로만 학습, 누수 점검 9가지, 게시판 글 등록일 357건 확인. 다만 "전날까지의 출력제어 여부와 전력거래소 전날 전망을 안다"는 가정은 있고 밝혔다 |
| 그 가정이 없으면? | 공개 자료만 쓰면 2026년 82일 중 74일을 알리지만 헛경보가 94번. 게시판에 전날까지 올라온 전망만 쓰면 65/82일 |
| 간단한 규칙으로 되지 않나? | PR-AUC '25 하반기 0.86 vs 0.52, '26년 0.73 vs 0.57. 2026년엔 규칙이 잡은 날 수는 더 많지만(73 대 69일) 헛경보도 더 많고(69 대 59번), 확률과 원인을 못 준다 |
| 전력거래소 전망이 있지 않나? | 전망을 낸 29일 중 28일 맞았지만(97%), 출력제어 82일 중 28일만 다뤘다. 나머지 54일 중 41일을 모델이 알렸다 |
| 2026년에도 맞나? | 출력제어 82일 중 69일(84%), 출력제어 시간 391시간 중 345시간(88%)을 전날 알렸다. 헛경보 59번, 그중 33번이 6월 14일 이후 (10월 31일까지 게시판 실적 반영, 11-25) |
| 2026 시험은 독립 시험인가? | 결과를 보기 전에 공개한 계획의 모델은 60/70일, 헛경보 67번. 전망 입력·확률·4단계는 그 뒤에 더했다. 둘을 구분해 말한다 |
| 원인 설명은 믿을 수 있나? | 모델이 무엇을 보고 확률을 올렸는지를 보여 줄 뿐, 실제 원인의 증명은 아니다 |
| 놓친 날은 왜 놓쳤나? | 송전망 제약, 원전 정비 같은 비공개 정보 때문인 날이 있다. 놓친 날은 평균 3.4시간으로 짧았다 |
| 누가 쓰나? | 태양광 발전사업자(정비 일정, ESS 충전 계획), 계통 운영 참고 |
| 출력제어를 막을 수 있나? | 아니다. 전날 알려서 버려질 전기를 ESS 충전·수요 이동으로 활용할 시간을 준다 |
